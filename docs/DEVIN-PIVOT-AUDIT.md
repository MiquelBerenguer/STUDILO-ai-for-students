# STUDILO / TutorIA — Code Audit and Agentic Pivot Readiness

## 1. Executive Summary

- The audited local product is a FastAPI modular monolith plus RabbitMQ workers and an auth-only Next.js shell, not an established end-to-end upload-and-click SaaS.
- Useful OCR, vector retrieval, structured LLM generation, exam construction, and scheduling code exists; existence does not establish production correctness.
- The most serious isolation defect is authenticated Solver retrieval over the shared collection without user/course filtering; ingestion also loses uploader identity in vector metadata.
- Exam generation uses fake mastery data, can lose RAG grounding and answer rules, and never persists completion; its status endpoint always returns `PROCESSING`.
- Auth refresh/logout are not fully integrated, and the frontend typecheck fails on both route handlers.
- Phase 0 is not complete: legacy services, duplicated clients, embedded credential defaults, HA infrastructure, and schema/migration drift remain.
- Some older findings are resolved or wrong: processor uses Sentinel and threaded MinIO operations; Node `pg` is asynchronous; the current gateway is Python.
- There is no implemented tool-calling agent loop, durable conversational/task memory, or proactive study trigger; request-supplied history and queue consumers are not substitutes.
- Pivot verdict: reuse selected capabilities behind corrected, authorized tool interfaces; add a small durable orchestrator, not a wholesale rewrite or an immediate multi-agent platform.

## 3. Component Inventory & Reuse Classification

### Classification rules

**REUSE AS-IS** means the core capability/primitive need not change specifically because the interaction becomes agentic; it is not a production-readiness certificate. **REUSE WITH REWORK** means retain capability but repair contracts, security, persistence or execution boundaries. **REPLACE** means replace the current implementation/shell, not necessarily its product purpose. **DISCARD** means redundant/inactive scaffolding, not a recommendation to delete files during this audit.

“Real” means substantive executable implementation, which can still contain defects. “Dead code” is relative to discovered imports and Compose entrypoints, not a claim nobody ever runs it manually. Each source module is represented below; closely related scaffolding/configuration is grouped explicitly. Empty package markers and binary assets have no meaningful code line to cite and are identified as such rather than assigned invented line numbers.

## 4. Agentic Pivot Readiness

### Working definition and limits

The proposed definition is reasonable if **autonomous** means making bounded decisions toward an explicit, authorized goal, not acting without constraints. A useful first system could have one LLM-driven coordinator with typed tools, persistent task/conversation records and approval gates. Multiple agents, a specific framework, and replacing HTTP are not prerequisites.

An LLM returning a question, schedule or structured JSON is not itself a tool-calling agent. Likewise a queue worker executes a preselected job; it does not decide which tool to call next. The largest general gap is durable orchestration with policy and feedback; for *proactive* study assistance, the missing scheduler/event-source layer is an additional essential structural gap.

### 4.1 Is there existing session/conversation memory?

**No durable conversational or agent memory is implemented in the inspected active path. There is some request-supplied history.**

- Solver accepts `conversation_history` and interpolates only its last three entries (`src/services/solver/schemas.py:5-11`; `src/services/solver/prompts.py:45-51`). It neither loads nor saves a conversation. This is client-carried context, not persistent memory.
- ProfessorAgent holds a constant system prompt on a singleton and returns a mock; it does not retain per-student turns (`src/services/learning/logic/professor_agent.py:8-46`).
- JWT access/refresh cookies represent authentication, not study memory. Backend token issuance/validation has no session table, refresh-token family or Redis session access (`src/api-gateway/app/core/security.py:24-91`; `src/api-gateway/app/services/auth_service.py:73-112`).
- Processor Redis stores expiring job status (`src/services/processor/app/core/redis_client.py:93-99`); grader's optional cache is disabled in its route factory (`src/services/learning/api/routes.py:45-46`). Neither is conversational memory.
- SQL/ORM cover accounts, courses, documents in SQL only, exams and questions; no conversation/messages/tool-log table (`src/shared/database/init.sql:48-167`; models:28-134). Migration comments reference older study tables but do not prove their existence or usage.

Thus API compute is largely per-request, but the system is not globally stateless: PostgreSQL/MinIO/Qdrant store durable product data, Redis stores transient job records, and the unused demo stores jobs in process. Deployment databases were not queried; undocumented external memory cannot be ruled out.

### 4.2 Is tool/function calling already implemented?

**No.** AIService uses `chat.completions.parse` with system/user messages and `response_format`, not `tools`, tool-call dispatch or an observe/plan/act loop (`src/services/ai/service.py:98-106,150-158,174-210`). Solver deterministically retrieves once, calls AI once, and assembles sources (`src/services/solver/service.py:28-64`). ExamGenerator deterministically fans out per question (`src/services/learning/logic/exam_generator.py:54-73`). ProfessorAgent does not call an LLM at all.

The processor requirements list `langchain` and text splitters (`src/services/processor/requirements.txt:43-45`), but no use of a tool registry, LangGraph, function-calling dispatch or durable agent graph was found. Dependency presence is not an abstraction.

**Reusable seams:** async `solve_doubt`, `generate_exam`, grading, schedule computation and OCR worker stages. Before tool exposure, each needs an explicit input/output contract, trusted actor/resource scope, time/cost/size limits, idempotency semantics and error/result records. External calendar/LMS writes and notifications need separately authorized connectors; no such connectors exist here.

### 4.3 Is there a generic task/plan state machine beyond documents/exams?

**No durable generic execution state machine. Even the two assumed machines are incomplete.**

- Documents have a SQL enum (`uploading/processing/ready/error`), not the SDD `pending/processing/ready/failed` lifecycle; gateway/worker never update those rows (`src/shared/database/init.sql:42-43,104-118`; documents route:60-97; PDF worker:77-161).
- Exams have an enum/string status in models but no active persistence transitions; endpoint returns a constant (`src/shared/database/models.py:12-16,94-111`; learning routes:240-249).
- Domain Exam uses `created`/`ready` independently (`src/services/learning/domain/entities.py:167-174`; generator:78-83).
- Legacy processor Redis includes `queued` and API-side `cancelled`, and demo jobs allow arbitrary strings (`processor/app/main.py:220-235,340-375`; `processor/simple_api.py:31-35,198-207`). Cancellation does not propagate to the worker. These are additional status representations, not a robust third task engine.
- Study planner returns session suggestions only; no plan persistence/execution/resume (`src/services/learning/logic/study_planner.py:42-100`).

**Generalization verdict:** reuse the lifecycle vocabulary and worker execution seams, not the existing exam/document table as a universal plan record. Agent tasks need parent/step relationships, checkpoints/results, attempts, versions/leases, waiting-for-user/approval, scheduled wakeups, cancellation, deadlines and idempotency. Document/exam records should remain domain artifacts linked to tasks. A string status plus task_id alone cannot represent resumable multi-step work.

### 4.4 Can the current Postgres schema house agent state naturally?

**Use existing account/course IDs for ownership; add new explicit tables for agent execution and memory.**

`users → students → courses` is a natural ownership/context spine. Existing `generated_exams` and `exam_questions` are output artifacts; `documents` is an ingestion artifact and is not yet ORM/migration-aligned. Planned mastery is learning evidence, not a conversation or tool ledger. The legacy `exams.content` JSONB addition in the single migration is neither the current GeneratedExam model nor a generic execution schema (migration:62-76).

A design direction, not an implementation specification: conversations/messages; tasks/steps or task events/checkpoints; tool invocations with validated inputs, bounded/redacted outputs, actor and attempt; approval/consent records; scheduler/connector cursors. Memory/preferences should have provenance, retention and deletion semantics. Keep sensitive connector credentials outside generic prompt/history JSON. Existing account/course FKs can anchor these records; avoid casually overloading exam JSON, Qdrant chunks or Redis TTL status.

Source schema evidence: `src/shared/database/models.py:28-134`, `src/shared/database/init.sql:48-159`, `src/shared/database/repositories.py:95-119`. Exact table design requires a product-approved autonomy/retention policy and reconciliation of current schema drift first.

### 4.5 Can the system act without a new human button click?

**It can finish a previously enqueued job without another click. It has no discovered proactive study trigger.**

RabbitMQ consumers are genuine event-driven execution (`src/services/processor/workers/pdf_worker_multi_queue.py:163-187`; exam worker:176-201), but production publishers are request handlers (`documents.py:40-91`; learning routes:206-235; processor main:141-263). APIs could be called programmatically; a literal browser click is not technically mandatory. What is absent is a scheduled study wakeup, LMS/calendar webhook/connector, due-task scanner or policy-driven follow-up producer.

No application cron/scheduler/webhook was found in source/Compose. CI push/PR triggers and healthchecks are operational automation, not autonomous student assistance (`.github/workflows/ci.yml:3-7`). Legacy vector config's backup interval is not an implemented timer (`src/services/vectordb/config/vectorConfig.js:179-185`).

**For the desired proactive interaction, this is a major structural gap:** there is no source of authorized wakeups and no durable coordinator to decide and record what should happen next. For a narrower user-initiated conversational agent, multi-step orchestration can begin from one request without proactive scheduling; the owner must choose which product is intended.

### 4.6 Are RabbitMQ and workers a viable substrate?

**Yes for heavy tool execution; no as a complete agent runtime by themselves.**

Retain RabbitMQ for OCR, embeddings and PDF generation if operationally justified. A coordinator can execute short read-only tools directly, dispatch longer ones to workers, save a checkpoint and resume on a completion event. RabbitMQ supports correlation/reply queues; a replacement broker is not fundamentally required. A long-lived in-request synchronous loop alone is insufficient for restarts, approval waits or scheduled resumptions.

Current blockers before that reuse:

1. Persistent commands and confirms exist for exams, but command-to-domain-state persistence is absent (`src/api-gateway/app/core/rabbitmq.py:36-66,96-108`; routes:211-235).
2. Exam worker catches errors inside `message.process()` and returns normally, allowing acknowledgement of a failed job (`src/services/learning/workers/exam_worker.py:97-99,173-174`). Declaring a DLQ does not fix swallowed exceptions.
3. PDF worker rethrows failures, but declares its queue without a retry/DLX policy; its producer does not request persistent message delivery (`pdf_worker_multi_queue.py:159-179`; documents.py:88-90). There is no durable completion event or status record.
4. Fixed exam queue TTL is five minutes; a future agent waiting for human approval must not be represented solely by a TTL-expiring broker message (`src/api-gateway/app/core/config.py:48`; rabbitmq.py:53-57).
5. Deterministic PDF chunk UUIDs help repeat upserts, and processed Markdown provides a limited OCR checkpoint (`pdf_worker_multi_queue.py:89-125,133-136`); neither provides transactional task idempotency or exactly-once external effects.

A small persisted coordinator is a reasonable initial direction. LangGraph or a durable-workflow engine is optional implementation support, not evidence the current queue must be replaced. The proposed multi-step pivot meets ADR-001's own “revisit when branching grows” condition (`../SDD-PLAN.md:72`); revisit deliberately after defining approval, resume and failure semantics. Notifications/streaming can improve UX, but SSE/WebSocket versus polling does not determine whether a system is agentic.

### 5.3 Infrastructure right-sizing and unresolved runtime claims

**ADR-003 has not been implemented.** The checkout still carries Postgres replica/HAProxy, Redis primary/replica/Sentinel, admin UIs, exporters/cAdvisor, Prometheus/Grafana and Elasticsearch/Kibana. No evidence of customer count, traffic, latency SLO, uptime target, operating budget or production deployment was provided. Calling all of it necessary for current scale would be speculation; calling redundancy inherently bad would also be wrong.

For the observed auth-only UI and incomplete backend lifecycle, the current default footprint is premature and partly miswired. A single, backed-up Postgres with explicit recovery objectives is more honest than round-robin writes to a standby. RabbitMQ/MinIO/Qdrant serve real capabilities, but can each be deliberately single-instance during validation if availability trade-offs are acknowledged. Redis is not used for gateway sessions or real grader caching and should earn its retention. Structured logs plus a few accurate metrics may be sufficient initially; retain existing useful Prometheus/Grafana pieces only if operated. `k8s/` adds no running footprint because it has no manifests.

Do not run the existing stack casually to “prove” readiness against valuable data: the replica startup command explicitly clears its data directory before re-seeding (`docker-compose.yml:80-88`), initialization SQL contains enum drops (`src/shared/database/init.sql:36-43`), and migration assumptions do not match fresh initialization. None of those operations was executed. Clean startup, failover, backup/restore, real OCR/AI quality and end-to-end completion remain **CANNOT VERIFY** until tested in an approved isolated environment.

## 6. Open Questions for the Product Owner

1. **Autonomy boundary:** Is the first product a user-initiated multi-step tutor, proactive scheduled assistance, or both? What may it do without approval, and what must always wait for the student?
2. **External effects:** May it create/update calendar events, send notifications, contact instructors or write to an LMS? Define separate consent, previews, cancellation and audit requirements; “agentic” does not itself authorize those actions.
3. **Source strategy:** If uploads are de-emphasized, where do notes, syllabus, assessment dates and availability come from? Which LMS/calendar provider is first, who owns access, and how are deleted/revoked materials removed from retrieval and memory?
4. **Grounding policy:** Must exams/answers be exclusively based on supplied material, or is marked general-knowledge fallback acceptable? Current README promise and Solver policy conflict. How should the tutor behave when OCR/retrieval is insufficient?
5. **Educational trust:** Are grades formative suggestions or authoritative assessment? Who validates answer keys, numeric tolerances, mastery updates and scheduling heuristics before an agent relies on them?
6. **Identity and privacy:** Does one account always equal one student? Are minors involved? Define retention/export/deletion for conversations, notes, derived memory and tool logs, and cross-course versus cross-student sharing rules.
7. **Human interaction:** How should clarifying questions, approvals, progress, failure/retry and final artifacts appear? Conversation and task views can coexist with file upload and explicit buttons; which existing interactions remain valuable?
8. **Deployment reality:** Which local changes are intended to become the actual master baseline? What database schema and Compose overrides are deployed, if any? Does an external gateway already enforce TLS, network isolation or rate limits?
9. **Reliability/cost:** What downtime/data-loss tolerance, expected usage and AI budget justify HA or a workflow engine? Which capabilities should stop when a per-task budget is exhausted?
10. **Plan conflict:** Is SDD-PLAN still authoritative after the pivot? Resolve its “single Redis” decision versus backend context's “remove Redis entirely,” and explicitly revise Phase 1/2 success criteria rather than silently inheriting a manual-generation roadmap.

## 7. Suggested Immediate Next 3 Steps

1. **Agree on one bounded agent outcome and its permissions.** For example, propose a study plan from an authorized course's notes, ask for missing dates, and request approval before calendar writes. Decide grounding, memory retention and cost limits. This validates the pivot without presupposing multiple agents or a new framework.
2. **Establish a trustworthy capability baseline before adding autonomy.** Prioritize student isolation/auth lifecycle, schema alignment, genuine questions/mastery inputs, correct generation/answer contracts, and durable job outcomes. Record explicitly which legacy services are retiring and preserve the active PDF worker. Validate these in an isolated environment with real completion and two-user isolation assertions, not mock-success polling.
3. **Specify and validate one thin durable orchestration slice.** Choose typed tool boundaries and task/step/approval records; use existing direct calls for short work and RabbitMQ for heavy execution, with completion events and resumability. Add exactly one authorized trigger if proactive behavior is part of the agreed outcome. Decide framework and infrastructure only from the resulting failure/resume requirements.

These are recommendations only. No implementation, configuration changes, migrations, service startup, PR, merge or push was performed as part of this audit.
